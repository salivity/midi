How DAWs Chase MIDI CC Values During Playback

Starting playback in the middle of a project can cause virtual instruments to sound incorrect if they miss earlier automation commands. Modern Digital Audio Workstations (DAWs) solve this issue through a mechanism known as MIDI Chase, or MIDI Event Chasing. This article explains how MIDI chase works, the underlying process DAWs use to scan timeline history, and how this feature maintains consistent sound design and mix balance during non-linear playback.

The Problem with Discrete MIDI Events

Unlike analog continuous voltages or audio waveform data, MIDI is an event-based protocol. Continuous Controller (CC) messages—such as CC1 (Modulation), CC11 (Expression), and CC7 (Volume)—are sent as discrete snapshots in time. When a DAW plays a sequence normally, it streams these single events chronologically to the receiving synthesizer or sampler.

If a user relocates the playhead to the middle of a track, the instrument only knows its current internal state. If a track features a volume fade-out or filter sweep earlier in the timeline, starting playback after that automation would normally leave the synth at whatever state it last received, causing sudden volume spikes or incorrect timbres.

The Mechanism: MIDI Event Chasing

To solve this, DAWs utilize MIDI Event Chasing. When the transport command is triggered at any point other than the project start, the DAW executes a brief, pre-playback scanning routine:

  1. Retroactive Timeline Scanning: Before activating the audio engine, the DAW's playback scheduler scans backward from the current playhead position across all active MIDI tracks.
  2. State Reconstruction: The DAW searches for the most recent occurrence of each MIDI message type on every channel. It looks for the latest value of:
    • MIDI Continuous Controllers (CC0 to CC127)
    • Pitch Bend data
    • Channel Pressure (Aftertouch)
    • Program Changes and Bank Select messages
    • Polyphonic Key Pressure
  3. Instantaneous State Transmission: The engine compiles the latest known values into a brief data burst. It transmits these updates immediately to the assigned virtual instruments and external hardware ports directly at the timestamp of the new playhead location.
  4. Playback Initiation: Once the receiver's internal parameters match the reconstructed state, standard timeline playback begins seamlessly.

Lookback Buffering and Performance Optimization

Scanning an entire project timeline from scratch every time the playhead moves would introduce transport latency, especially in large orchestral templates with hundreds of tracks. Modern DAWs optimize this using state caching and indexed event lists.

Instead of scanning all previous bars, the DAW maintains an indexed lookup table of event positions. When the playhead moves, the DAW only queries the index for the latest value preceding the target locator. In addition, DAWs generally send only the single latest value for any given controller rather than replaying the entire history of continuous movements, keeping the initialization burst lightweight and avoiding MIDI buffer overruns.

Chasing Notes vs. Chasing Controllers

While CC chasing is almost universally enabled by default, most DAWs treat MIDI Note-On events separately.

  • Controller Chasing: Generally safe and recommended because sending a static parameter value (such as CC1 = 64) simply defines an instrument's sound without triggering new audio.
  • Note Chasing: Optional in DAW preferences. If enabled, splitting or starting playback in the middle of a sustained pad or chord will force the DAW to generate a Note-On event so the sustain is not lost. However, this can inadvertently trigger transient attacks (such as a piano strike or drum hit) midway through the sample, which can disrupt the intended performance.
