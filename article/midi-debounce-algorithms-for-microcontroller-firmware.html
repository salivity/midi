MIDI Debounce Algorithms for Microcontroller Firmware

Mechanical switches, buttons, and velocity-sensitive keybeds exhibit physical contact bounce that can produce rapid, unintended electrical transitions. In musical instruments, these microsecond-level fluctuations translate into erratic MIDI double-triggering, sending duplicate Note-On and Note-Off events that ruin musical articulation and waste bandwidth. This guide outlines the essential firmware debounce algorithms used in microcontroller-based MIDI devices, examining their mechanics, latency trade-offs, and implementation strategies to maintain real-time responsiveness while eliminating false triggers.

1. Immediate Trigger with Lockout (Re-Trigger Inhibit)

For musical applications, latency is the primary concern; players can perceive delays as small as 5 to 10 milliseconds. The Immediate Trigger with Lockout algorithm prioritizes zero-latency response on the initial key press.

  • How it works: When a state transition from idle to pressed is detected, the microcontroller immediately transmits a MIDI Note-On message and starts a non-blocking hardware or software timer (the lockout window, typically 5 to 20 ms). During this window, all subsequent state changes on that specific input pin are ignored. Once the timer expires, the pin is sampled again to confirm its steady-state.
  • Why it works for MIDI: The physical action of pressing a switch creates contact bounce after the initial contact is made. By firing the MIDI event on the very first falling or rising edge and ignoring the immediate aftermath, latency is reduced to practically zero microseconds without generating redundant notes.
// Conceptual Immediate Trigger implementation
void handleButton(uint8_t pinIndex, uint32_t currentTime) {
    bool currentReading = digitalRead(pins[pinIndex]);
    
    if (currentReading == PRESSED && buttonState[pinIndex] == RELEASED) {
        if (currentTime - lastStateChangeTime[pinIndex] >= LOCKOUT_TIME_MS) {
            buttonState[pinIndex] = PRESSED;
            lastStateChangeTime[pinIndex] = currentTime;
            sendMidiNoteOn(notes[pinIndex], 127);
        }
    } else if (currentReading == RELEASED && buttonState[pinIndex] == PRESSED) {
        if (currentTime - lastStateChangeTime[pinIndex] >= LOCKOUT_TIME_MS) {
            buttonState[pinIndex] = RELEASED;
            lastStateChangeTime[pinIndex] = currentTime;
            sendMidiNoteOff(notes[pinIndex], 0);
        }
    }
}

2. Asymmetric Debouncing (Fast Attack, Stable Release)

Symmetric debouncing applies the same delay or filtering algorithm to both press (attack) and release (decay). However, mechanical switch bounce characteristics often differ substantially between closure and opening.

  • How it works: This algorithm uses an immediate trigger or short lockout for the Note-On transition (fast attack) to minimize latency, combined with an integrating counter or a longer lockout period for the Note-Off transition (stable release).
  • Why it works for MIDI: When a key is released, spring vibration can momentarily reconnect contacts, causing an instant, false re-strike. Increasing the release debounce threshold prevents secondary Note-On messages without compromising the attack feel of the instrument.

3. Shift-Register State History (Bitmask Filtering)

For matrix scanning or high-density MIDI controllers (such as 64-button step sequencers or multi-octave keyboards), saving memory and processing overhead is crucial. The shift-register technique stores recent pin readings as a bitfield.

  • How it works: At fixed intervals (typically generated by a 1 kHz timer interrupt), the state of the pin is shifted into an 8-bit integer:

    \[\text{history} = (\text{history} \ll 1) \mid \text{currentPinValue}\]

    A MIDI event is dispatched only when the bitfield matches a definitive bitmask pattern:

    • Note-On Trigger: history == 0b10000000 (transition to pressed across consecutive samples)
    • Note-Off Trigger: history == 0b01111111 (transition to released)
    • Steady State: 0xFF (held) or 0x00 (idle)

  • Why it works for MIDI: It acts as a moving-window digital low-pass filter that requires minimal CPU cycles. It can be computed in parallel across entire microchip ports using native bitwise operations.

4. Integrating Continuous Counters

Integrating debouncers accumulate evidence of a switch state change rather than relying on boolean logic or fixed lockouts.

  • How it works: A counter variable is initialized at zero. Every polling period (e.g., 1 ms), the algorithm checks the pin. If the switch reads as pressed, the counter increments by one; if released, it decrements by one. The counter is clamped between zero and an upper threshold (e.g., 5).
  • State Change: When the counter hits the upper threshold, the official state becomes "pressed," sending a Note-On. When it drops to zero, the official state returns to "released," sending a Note-Off.
  • Why it works for MIDI: This method is robust against continuous electrical noise, such as inductive coupling from nearby stage lighting, power supplies, or motor faders, which could otherwise falsely break a lockout-based system.

5. Dual-Contact Velocity Timing Debounce

Full-sized synthesizer and digital piano keybeds use two or three physical contacts per key (rubber domes over PCB carbon contacts) to measure velocity by calculating transit time (\(v \propto \frac{1}{\Delta t}\)).

  • How it works: The algorithm treats contact A (high contact) and contact B (low contact) as an interdependent state machine:
    1. Key rests at idle: Both A and B are open.
    2. Travel begins: Contact A closes. A high-resolution microsecond timer begins.
    3. Bottom of keybed: Contact B closes. The timer stops, transit time is converted to MIDI velocity (1–127), and Note-On is emitted.
  • Debounce Role: The state machine naturally acts as a hardware-state debounce filter. Once Contact A activates, Contact B cannot trigger a Note-On without the timer initiating first. If Contact B bounces, the firmware enters an active "playing" state and ignores subsequent B-strikes until Contact A opens first, completely eliminating velocity calculation errors and repetitive double-triggers.

Implementation Guidelines

  • Sample Rates: Run debouncing routines on dedicated hardware timer interrupts set between 500 Hz (2 ms) and 2 kHz (0.5 ms). Avoid using polling loops in main() that vary with MIDI output throughput.
  • Avoid Blocking Code: Never employ hard delays (such as delay() or busy-wait loops) inside debounce logic; blocked execution creates MIDI jitter across other inputs and throttles the USB/serial transmission buffer.
  • Lockout Tuning: Start with a 15 ms lockout for standard silicone pad controllers, 8 to 10 ms for mechanical keyboard switches, and 20 to 30 ms for heavy-duty metal footswitches.
