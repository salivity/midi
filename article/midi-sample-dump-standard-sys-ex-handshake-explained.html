MIDI Sample Dump Standard: SysEx Handshake Explained

This article explores how Universal Non-Real-Time System Exclusive (SysEx) messages resolve hardware interoperability issues through the MIDI Sample Dump Standard (SDS). By establishing a structured, two-way communication protocol, SDS enables different MIDI samplers to negotiate sample rates, word lengths, and data transmission regardless of manufacturer. Readers will learn the technical mechanics of the handshake process, the role of specific packet headers, and how bidirectional flow control ensures error-free sample transfers over standard MIDI connections.

The Challenge of Proprietary Sample Transfers

In the early era of digital sampling, hardware manufacturers used proprietary System Exclusive formats to transmit audio data. Because a Roland, Akai, or E-mu sampler used unique SysEx formats, transferring raw audio samples between different brands or between a computer and a sampler required specialized, machine-specific software. To solve this fragmentation, the MIDI Manufacturers Association defined the MIDI Sample Dump Standard (SDS) using Universal Non-Real-Time System Exclusive messages.

The Universal Non-Real-Time SysEx Framework

Universal Non-Real-Time SysEx messages use a dedicated MIDI standard structure starting with the SysEx status byte F0h, followed by the Universal Non-Real-Time identifier 7Eh. Because sample transfers do not require immediate, sample-accurate playback timing, they are categorized as non-real-time.

Within this framework, sub-ID bytes dictate the nature of the transmission. For SDS, the primary sub-ID 05h specifies Sample Dump operations, followed by secondary sub-IDs that define whether a message is a header, a data packet, a request, or a handshake state (such as ACK or NAK).

The Handshake Sequence

The standardization of sample dumps relies on closed-loop, bidirectional communication between the sending and receiving devices. This handshake sequence proceeds through distinct phases:

  1. Dump Header (01h): The transmitter sends metadata detailing the sample slot number, sample format (typically 8 to 24 bits), sample period (sample rate represented in nanoseconds), total sample length in words, loop start and end points, and loop types.
  2. Acceptance or Rejection: The receiving sampler evaluates the header against its internal memory and architectural limits. If compatible, it replies with an ACK (Acknowledge, sub-ID 7Fh). If the format is unsupported, it transmits a CANCEL (7Dh) message, aborting the transfer before data is sent.
  3. Data Packet Transmission (02h): Once accepted, the sender transmits sample data in small, numbered packets—usually 120 bytes of payload representing 7-bit converted audio data. Each packet includes a packet counter and an error-checking checksum.
  4. Flow Control Handshaking: Upon receiving a packet and verifying the checksum, the receiver issues an ACK to request the next sequential packet. If a checksum error occurs or a packet is dropped, the receiver sends a NAK (Negative Acknowledge, sub-ID 7Eh), prompting the sender to retransmit that specific packet. If the receiver needs time to process or write data to memory, it issues a WAIT (7Ch) message to pause transmission.

Cross-Manufacturer Uniformity

By defining strict, byte-level rules for handshaking, Universal Non-Real-Time SysEx detached sample transmission from proprietary chipsets and storage mediums. The standard forces different hardware samplers to normalize audio data into an identical packetized structure, transforming what was once a manufacturer-dependent process into a reliable, universal standard across the electronic music industry.
