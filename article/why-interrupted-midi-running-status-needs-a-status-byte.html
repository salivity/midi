Why Interrupted MIDI Running Status Needs a Status Byte

Running status is an optimization feature in the MIDI 1.0 specification designed to conserve bandwidth by omitting redundant status bytes during continuous, identical message streams. When an interrupting MIDI event occurs, the receiver's internal state is altered or reset, making it impossible to correctly decode subsequent data without explicitly re-establishing the target command. Transmitting a new status byte immediately after an interruption is strictly required to prevent catastrophic data misinterpretation, stuck notes, and dropped commands.

In standard MIDI communication, a complete Channel Voice message consists of a status byte (which defines the action and the channel, such as Note On for Channel 1) followed by one or two data bytes (such as pitch and velocity). Under running status rules, if a transmitter sends multiple consecutive messages of the exact same type and channel, it can omit the status byte after the first message. The receiving device stores this initial status byte in a dedicated running status buffer and automatically applies it to all incoming raw data bytes.

This mechanism relies entirely on the receiver maintaining an unbroken state. If another MIDI event interrupts the stream, this state is fundamentally compromised:

  • Channel Voice Overwrites: If a different Channel Voice message arrives—such as a Note On for a different channel, a Control Change, or a Pitch Bend—the receiver updates its running status buffer to reflect the new command. If the transmitter subsequently returns to sending data bytes from the original sequence without providing a new status byte, the receiver will apply the interrupting status to those bytes. For example, pitch and velocity data meant for a note could be misparsed as controller numbers and values, causing unpredictable sonic glitches.
  • Buffer Invalidation via System Messages: System Common messages (such as Song Select or Tune Request) and System Exclusive (SysEx) messages explicitly clear the running status buffer entirely. If a stream is interrupted by one of these messages, the receiver no longer possesses an active status byte in its buffer. Any raw data bytes received immediately afterward are considered orphaned data and are discarded by the receiver, resulting in missing notes or ignored performance data.

While MIDI System Real-Time messages (such as MIDI Clock and Active Sensing) are an exception that can weave into a running status stream without clearing the buffer, any other interrupting event breaks the continuity.

Because the receiver cannot guess when a sender has switched back to an earlier context, the transmitter is mandated by the MIDI specification to send a fresh status byte the moment it resumes the prior stream. This guarantees that the receiver updates its running status register to the correct command and channel before parsing any subsequent data bytes.
