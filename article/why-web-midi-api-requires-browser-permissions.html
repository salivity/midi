Why Web MIDI API Requires Browser Permissions

The Web MIDI API enables web applications to interact directly with Musical Instrument Digital Interface (MIDI) hardware, bridging the gap between web software and external audio equipment like synthesizers, drum pads, and controllers. While this capability allows for sophisticated browser-based digital audio workstations, it also creates direct communication pathways to external hardware. Because this low-level interaction poses severe security and privacy threats—including malicious firmware modification, hardware hijacking, and persistent cross-site tracking—modern web browsers require explicit user permission before granting access to connected MIDI devices.

System Exclusive (SysEx) Vulnerabilities

The most significant security hazard within the MIDI protocol is the use of System Exclusive (SysEx) messages. Unlike standard MIDI signals that transmit basic musical instructions such as note activations or pitch modulation, SysEx messages are vendor-specific commands intended to configure internal device settings.

Through SysEx communication, an external program can read internal memory, alter global device configurations, and transmit firmware updates. Without browser permission prompts, a malicious website running in the background could send rogue SysEx payloads to reflash a connected instrument's firmware. This could permanently disable (brick) the equipment or inject malicious persistent code into devices with programmable microcontrollers.

Hardware Fingerprinting and Tracking

Browsers enforce permissions to prevent unauthorized digital fingerprinting. When a web application queries the Web MIDI API, the interface returns detailed device metadata, including:

  • Device manufacturer and vendor names
  • Model identifiers and product names
  • Specific port configurations and connection states

Because physical MIDI gear is relatively uncommon compared to standard peripherals, the presence of specific musical hardware provides an exceptionally distinct tracking signal. Data brokers and malicious trackers could query connected MIDI devices silently, creating a persistent identifier to track users across unrelated websites, effectively bypassing incognito modes, VPNs, and standard cookie protections.

Control of Non-Musical Hardware

The MIDI protocol is widely adopted outside the realm of musical performance. Many industrial systems, stage lighting rigs (via DMX-to-MIDI converters), video switchers, and specialized input interfaces rely on MIDI commands for real-time control.

Granting an untrusted webpage unfettered access to the MIDI subsystem could allow it to manipulate physical infrastructure. A malicious script could trigger high-intensity stage lighting, actuate mechanical equipment, or interfere with ongoing live broadcast automation connected to the host computer.

Physical Damage and Auditory Risks

Unchecked MIDI transmission can pose physical risks to both equipment and human hearing. A rogue script could rapidly send commands setting volume controls, amplifier gains, or digital resonance filters to their maximum levels while simultaneously triggering loud chords. These sudden, unexpected sound bursts can cause acoustic trauma to users wearing headphones and potentially blow out connected studio monitors, subwoofers, and PA systems.

Modern Browser Permission Policies

Originally, browsers like Google Chrome allowed standard Web MIDI access silently, only prompting the user when an application requested sysex: true. However, due to rising fingerprinting concerns and the security overlap between standard messages and internal device memory, the W3C Audio Working Group and major browser vendors updated their security models.

Modern browsers treat all MIDI interactions as powerful features, placing basic MIDI access alongside camera, microphone, and geolocation permissions. Users must actively click an explicit prompt to grant access, ensuring that low-level hardware remains isolated from untrusted web content.
