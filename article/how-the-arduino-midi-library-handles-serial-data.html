How the Arduino MIDI Library Handles Serial Data

The open-source Arduino MIDI Library bridges the gap between low-level serial communication and high-level music programming by wrapping raw byte manipulation inside an object-oriented C++ framework. Instead of requiring developers to manually configure hardware UART registers, construct multi-byte packets, and decode binary status messages, the library provides a clean API centered around familiar musical concepts. By managing serial transport configuration, byte serialization, running status, and incoming packet parsing behind the scenes, the library transforms raw serial data streams into structured, event-driven function calls.

Hardware and Transport Layer Decoupling

At the lowest level, standard 5-pin DIN MIDI operates asynchronously over serial at a specific rate of 31,250 baud. The Arduino MIDI Library abstracts this hardware dependency by utilizing a templated transport layer. Rather than hardcoding calls to hardware UART registers, the library accepts a generic serial class—such as HardwareSerial or SoftwareSerial—as a parameter when instantiating the MIDI interface.

During initialization via MIDI.begin(), the library automatically configures the underlying serial port to 31,250 baud and 8-N-1 (8 data bits, no parity, 1 stop bit) communication parameters. This transport abstraction enables the core MIDI logic to remain identical whether transmitting over standard hardware pins, software-emulated pins, or alternative transports like USB MIDI.

Outbound Message Marshalling

Standard MIDI channel voice messages consist of a status byte followed by one or two data bytes. A status byte encodes both the message type and the target MIDI channel (1 through 16), while data bytes contain parameters like note numbers, velocity, or controller values:

  • Status Byte: High bit set (1xxx xxxx), containing the command nibble (e.g., 0x90 for Note On) and the 0-indexed channel nibble (0x0 to 0xF).
  • Data Bytes: High bit clear (0xxx xxxx), limiting payload values from 0 to 127.

The library encapsulates this bitwise math inside high-level outbound functions like MIDI.sendNoteOn(), MIDI.sendControlChange(), and MIDI.sendProgramChange(). When a developer calls:

MIDI.sendNoteOn(60, 127, 1);

the library executes internal bitwise operations to construct the packet:

  1. It combines the NoteOn command identifier (0x90) with the channel minus one (channel - 1) using a bitwise OR operation, creating the status byte 0x90.
  2. It validates that the note number (60) and velocity (127) fall within the valid 7-bit MIDI range (0–127).
  3. It passes these three structured bytes sequentially to the transport layer's write() method.

This eliminates the need for developers to manually compute channel offsets or mask bit patterns.

Inbound Stream Parsing via Finite State Machine

Inbound MIDI data arrives as an unstructured stream of individual bytes over serial. Messages can be interrupted by real-time bytes (such as MIDI clock signals) or abbreviated by "Running Status"—a MIDI feature where successive messages of the same type omit the status byte.

The library's MIDI.read() method processes this stream byte-by-byte using an internal finite state machine (FSM). As each byte is read from the serial buffer, the state machine tracks:

  • Whether the byte is a status byte, a data byte, or a real-time message.
  • How many data bytes are required to complete the current message type.
  • The active running status if subsequent data bytes arrive without a preceding status byte.

The parser filters and buffers incoming bytes until a complete message is assembled. Real-time messages are intercepted and handled immediately without resetting the state of standard voice messages. Once the FSM determines that all required bytes for a command have arrived, it packages the payload into a structured Message struct containing the message type, channel, data fields, and validity flags.

Event-Driven Callbacks and Type Safety

To fully insulate the developer from polling buffers and checking message flags manually, the Arduino MIDI Library implements an event-driven architecture using function pointers.

Developers can register custom callback functions using methods such as MIDI.setHandleNoteOn() or MIDI.setHandleControlChange(). When MIDI.read() completes parsing a valid message, it checks whether a corresponding callback function is registered. If so, it invokes the user function, passing the unpacked values (such as channel, pitch, and velocity) as native C++ data types.

By handling bit shifting, buffering, state management, and error checking behind these structured abstractions, the Arduino MIDI Library turns bare-metal microcontrollers into reliable, readable musical instruments.
