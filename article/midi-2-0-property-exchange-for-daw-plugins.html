MIDI 2.0 Property Exchange for DAW Plugins

MIDI 2.0 Property Exchange revolutionizes hardware-software workflows by enabling bidirectional, metadata-rich communication between hardware controllers and Digital Audio Workstation (DAW) plugins. Through standardized inquiry protocols and structured JSON data payloads, a hardware controller can discover what plugin it is linked to, query its internal parameter list, and display accurate parameter names, current values, and data formats directly on hardware screens without requiring manual MIDI mapping or custom templates.

The Foundation: MIDI Capability Inquiry (MIDI-CI)

Before any parameter names are transmitted, the hardware controller and the DAW must establish a mutual understanding of each other's capabilities. This process is handled by MIDI Capability Inquiry (MIDI-CI).

When a MIDI 2.0 device is connected via a Universal MIDI Packet (UMP) connection, it initiates a discovery handshake. Through this handshake, the hardware confirms whether the DAW host supports the three pillars of MIDI-CI: Profile Configuration, Protocol Negotiation, and Property Exchange. Once both endpoints negotiate and agree on Property Exchange support, the pathway is open for metadata retrieval.

The Mechanism of Property Exchange (PE)

Property Exchange acts as an application-layer protocol within the MIDI standard, utilizing JSON-formatted payloads transmitted inside MIDI System Exclusive (SysEx) messages. Unlike legacy MIDI 1.0, which was restricted to basic 7-bit values tied to arbitrary Continuous Controller (CC) numbers, Property Exchange standardizes how software and hardware describe parameters to each other.

The process of pulling parameter names into hardware knobs follows a standard request-response architecture:

  1. Resource Discovery: The hardware controller sends a Property Exchange request asking for the plugin's property list (the schema of available parameters).
  2. DAW/Plugin Translation: The DAW acts as a bridge. It intercepts the hardware request, checks the exposed automation tree of the target VST, AU, or native plugin, and translates the plugin's parameter descriptors into standardized JSON.
  3. JSON Response: The DAW sends a Property Exchange reply back to the hardware. This payload includes an array of objects detailing the parameter ID, human-readable name (e.g., "Filter Cutoff"), current value, data type (float, integer, enum), minimum/maximum ranges, and measurement units (e.g., "Hz" or "dB").

Dynamic Assignment and Display Updating

Upon receiving the JSON response, the hardware controller's internal microprocessor parses the data and dynamically binds each physical control to the corresponding parameter:

  • Name Resolution: The hardware extracts the string assigned to the parameter name (such as "Resonance" or "Attack") and routes it directly to the OLED, LCD, or scribble strip screen positioned above or below the knob.
  • Control Binding: The hardware maps the physical rotary encoder's movements to the high-resolution MIDI 2.0 controller messages that correspond to that specific parameter ID.
  • Value Formatting: Because the JSON payload defines the units and value ranges, the hardware can display exact values (such as "1.2 kHz") rather than arbitrary numbers from 0 to 127.

Bidirectional Synchronization

Property Exchange also supports dynamic subscription models. If a user adjusts a parameter using a mouse on the computer screen or switches to a completely different plugin, the DAW issues a Property Exchange update or notifies the hardware that the resource has changed. The hardware updates its displays in real time, ensuring that the physical labels and values continuously mirror the active state of the software plugin.
