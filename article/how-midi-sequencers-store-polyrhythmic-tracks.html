How MIDI Sequencers Store Polyrhythmic Tracks

MIDI sequencers store polyrhythmic tracks with differing lengths and independent loop points by decoupling individual track timelines from the global transport clock. Instead of forcing all data into a uniform measure-based grid, the sequencer treats each track as an autonomous data stream governed by its own timebase, loop markers, and playhead position. By utilizing modular data structures, high-resolution tick counters, and modulo arithmetic, modern sequencers can play back sequences of arbitrary lengths—such as a 7-step hi-hat pattern alongside a 16-step kick drum—while maintaining continuous synchronization.

Independent Track Architecture

At the code level, a sequencer models each track as a distinct object or data structure rather than a flat, monolithic list of MIDI events. A typical polyrhythmic track structure contains:

  • A Local Event List: A buffer of MIDI events (Note On, Note Off, CC values) stored with timestamps relative to the track's local origin rather than the master project timeline.
  • Local Boundary Pointers: Explicit properties defining loop_start, loop_end, and track_length, typically measured in internal clock ticks (Pulses Per Quarter Note, or PPQN).
  • A Local Playhead/Phase Accumulator: A floating-point or integer variable that tracks the current read position within that specific track.
  • A Clock Multiplier/Divider: A rational number (e.g., 3/2, 5/4, or 1/1) that scales incoming clock pulses to adjust the playback rate for metric polyrhythms.

By isolating these parameters inside each track's memory space, changing the loop length or playback rate of one track has zero structural impact on any other track in the project.

Delta Ticks and Modulo Looping

Internal sequencer engines rely on a high-resolution integer clock running at a standard rate, such as 960 or 1920 PPQN. When handling independent loop points, the sequencer calculates playback using modulo arithmetic to determine which events to trigger.

When the global transport advances, each track updates its internal phase counter:

\[\text{Current Position} = (\text{Elapsed Track Ticks}) \pmod{\text{Loop Length}}\]

Because the loop calculation is evaluated per-track, track lengths do not need to share a common denominator. If Track A has a loop length of 1,920 ticks (a standard 4/4 measure at 480 PPQN) and Track B has a loop length of 2,400 ticks (a 5-beat phrase), the sequencer resets each track's read pointer back to its local loop_start as soon as its unique limit is reached. The events are kept in a sorted priority queue or flat array, and the read pointer fires any event whose timestamp falls within the current processing block.

Polymeter vs. Polyrhythm Storage

Sequencers differentiate between polymetric tracks (different phrase lengths running at the same tempo) and true polyrhythmic tracks (different tempos or subdivisions running concurrently):

  • Polymetric Storage: Events share the exact same tick duration (e.g., a sixteenth note is always 120 ticks). The file or memory buffer simply stores different terminal boundaries for each track. The tracks naturally shift out of phase over time because the modulo reset occurs at different intervals.
  • Polyrhythmic Storage: The sequencer stores time-scaling factors or uses independent PPQN definitions per track. For instance, playing five notes in the space of four notes requires the sequencer to store either fractional tick durations or multiply incoming master clock ticks by a factor of \(5/4\) before updating the track's playhead.

Project File Serialization

Standard MIDI Files (SMF Type 1) represent events sequentially along a single timeline and lack native, standardized support for independent track loops. Consequently, sequencers store polyrhythmic configurations within their own proprietary file formats (such as XML, JSON, SQLite databases, or custom binary files).

In these formats, the sequencer serializes:

  1. The Raw Pattern Data: The note values and their positions inside a normalized loop container (e.g., 0 to \(N\) ticks).
  2. Clip and Track Metadata: The explicit loop points, start offsets, time signatures, and play rates assigned to the container.
  3. Playback Rules: Instructions detailing whether a clip should loop infinitely, truncate, or re-trigger based on global bar markers.

When loading the file, the sequencer reconstitutes the independent virtual playheads, feeds them into the main scheduling loop, and relies on the playback engine's real-time math to keep the disparate patterns in sync.
