CoreMIDI Background Execution Limits in iOS

CoreMIDI applications running on iOS face strict operational boundaries imposed by the operating system’s background execution models. While iOS permits certain apps to run outside the foreground to ensure continuous playback or recording, maintaining reliable real-time MIDI communication requires satisfying specific background modes, handling hardware state transitions, and navigating operating system resource constraints. Understanding how iOS regulates background processing, audio engine coupling, Bluetooth Low Energy (BLE) MIDI, and memory management is essential for developing stable music creation tools.

The Audio Background Mode Dependency

CoreMIDI by itself lacks a dedicated background execution capability. In iOS, an application cannot request a background mode exclusively for processing or transmitting MIDI data. To prevent an active MIDI session from being suspended immediately when the user switches apps or locks the screen, the application must declare the audio value in its UIBackgroundModes array within the Info.plist.

Declaring this mode is insufficient on its own; the app must also maintain an active, running audio session via AVAudioSession. If an application is purely a MIDI controller or processor that produces no sound, it must still initialize an audio engine or an uninterrupted silent audio output stream. If this audio stream stops, iOS suspends the application within seconds, cutting off all incoming and outgoing MIDI packets.

CPU Throttling and Real-Time Jitter

iOS optimizes battery life and thermal output by actively throttling the CPU and demoting background thread priorities. When an application moves to the background:

  • Thread Scheduling: Even if an app utilizes real-time audio threads, background threads receive less scheduler priority than the active foreground application.
  • Latency and Jitter: MIDI event processing requires millisecond-level precision. Background throttling often causes time-jitter, irregular packet transmission intervals, and delayed handling of time-critical messages like MIDI Clock, Start, and Stop commands.
  • Buffer Underruns: If the application performs complex sequencing, routing, or processing alongside MIDI, processing spikes can exceed the reduced compute budget, leading to dropped messages or system-initiated termination.

Bluetooth LE MIDI Limitations

Bluetooth Low Energy MIDI (BLE MIDI) experiences distinct hurdles in the background. While the CoreBluetooth framework supports background central and peripheral roles, maintaining persistent BLE MIDI connections under constrained states introduces vulnerabilities:

  • Connection Drops: When the system experiences memory or power pressure, backgrounded BLE connections can be terminated or deferred by the OS.
  • Packet Throttling: Backgrounded BLE peripheral connections are subjected to relaxed connection intervals, directly increasing latency and reducing throughput for high-density MIDI streams, such as pitch bend and polyphonic aftertouch.
  • Scanning Restrictions: If an app is backgrounded, it cannot discover new BLE MIDI devices effectively, as the OS aggregates and throttles scanning intervals to conserve power.

Memory Pressure and Jetsam Termination

iOS enforces aggressive memory management through its Jetsam mechanism. Background applications are the first candidates for termination when the foreground application demands additional RAM:

  • Sudden Eviction: CoreMIDI apps running in the background can be killed silently without prior warning or state-saving notifications if memory limits are exceeded.
  • Virtual Port Invalidation: When a background MIDI app is terminated by Jetsam, its virtual CoreMIDI sources and destinations disappear instantly from the system. Other active apps lose their connections to these endpoints, causing broken routing across the entire inter-app audio ecosystem.

Hardware and Hot-Plugging State Changes

When an iOS device connects to external USB MIDI interfaces via the Camera Connection Kit or direct USB-C, handling hardware state in the background becomes unreliable. If a hardware interface is disconnected or reconnects while the app is in the background, CoreMIDI notifications may be delayed or fail to process correctly until the user brings the app back to the foreground, potentially freezing the input/output pipeline.
