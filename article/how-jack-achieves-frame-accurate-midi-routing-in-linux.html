How JACK Achieves Frame-Accurate MIDI Routing in Linux

The JACK Audio Connection Kit achieves frame-accurate, low-latency MIDI routing by integrating MIDI events directly into its real-time audio processing graph. Rather than processing MIDI as an asynchronous serial stream through separate system timers, JACK encapsulates MIDI messages inside discrete audio cycle buffers, timestamping each event to an exact audio frame. This unified execution architecture ensures that MIDI routing suffers zero relative jitter against audio, maintaining sub-millisecond synchronization across complex Linux digital audio workflows.

Synchronous Processing Graph

JACK executes signal routing through an acyclic directed graph where all connected applications are ordered by processing dependency. In each period—defined by the hardware buffer size (e.g., 64, 128, or 256 frames)—the JACK engine triggers a global cycle via a real-time process callback (jack_process).

MIDI ports are first-class citizens in this graph. Because the audio and MIDI streams are processed simultaneously in the exact same callback cycle, MIDI messages are never delayed to a secondary thread or queued behind audio computation. They travel downstream alongside the audio buffers with deterministic execution boundaries.

Sample-Frame Timestamping

Traditional Linux MIDI architectures, such as the ALSA Sequencer, often rely on millisecond-resolution system clocks or interrupt timers. When audio buffer underruns, CPU throttling, or thread scheduling shifts occur, ALSA MIDI events can drift relative to the audio timeline.

JACK avoids this by assigning every MIDI event a sample-relative offset:

  • Each MIDI event buffer is tied to an audio buffer of size \(N\) frames.
  • When a MIDI event is written to a port buffer using the JACK MIDI API (jack_midi_event_write), it requires an explicit frame-offset parameter ranging from \(0\) to \(N-1\).
  • Receiving applications unpack events via jack_midi_event_get, reading the exact frame index where the note-on, control change, or pitch bend occurs within that slice of time.

This design guarantees absolute frame accuracy: an event assigned to frame 32 of a 128-frame period is rendered precisely at that sample position by the downstream synthesizer or plugin, eliminating jitter caused by serial port timing or operating system scheduling delays.

Shared Memory and Lock-Free Data Transfer

Inter-process communication (IPC) introduces latency if it requires context switching into kernel space. JACK bypasses this overhead by allocating shared memory regions for client input and output buffers via POSIX shared memory primitives.

MIDI messages within JACK are converted into raw event buffers stored directly in these shared memory segments. The transmission between the sending client and receiving client requires no kernel intervention, dynamic memory allocation, or socket copying. Furthermore, communications between threads and clients utilize lock-free atomic structures (such as single-reader, single-writer lock-free ring buffers), preventing priority inversions and thread blocking during MIDI transfer.

Real-Time POSIX Threading

To ensure low latency without dropouts (xruns), the JACK daemon and its client process threads execute with POSIX real-time priorities (SCHED_FIFO or SCHED_RR).

By pairing high-priority real-time threads with memory locking (mlockall), JACK prevents its processing threads from being preempted by standard user space tasks or paged to disk swap. As a result, the entire sequence—reading input hardware, routing MIDI buffers across client nodes, and outputting to sound synthesis engines—completes reliably within the strict microsecond deadlines imposed by low buffer sizes.
