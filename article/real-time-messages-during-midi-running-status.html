Real-Time Messages During MIDI Running Status

This article examines how the MIDI protocol handles the interruption of an active running status sequence by an unexpected System Real-Time message. It details the underlying specifications that govern receiver behavior, explains why these interruptions occur, demonstrates how running status buffers remain intact, and highlights the single critical exception to this standard rule.

The Mechanics of Running Status

Running status is a bandwidth-saving feature defined in the MIDI 1.0 specification. When multiple consecutive Channel Voice messages share the same status byte—such as a sequence of Note On or Control Change events—the transmitter can omit the status byte after the first message. The receiving device stores the most recent status byte in its buffer and automatically applies it to incoming pairs or single data bytes.

Under standard conditions, any new non-real-time status byte (values from 0x80 to 0xF7) overwrites or clears this buffer, terminating the active running status sequence.

How System Real-Time Messages Behave

System Real-Time messages occupy the byte range 0xF8 to 0xFF. These include time-critical signals such as:

  • Timing Clock (0xF8)
  • Start (0xFA)
  • Continue (0xFB)
  • Stop (0xFC)
  • Active Sensing (0xFE)
  • System Reset (0xFF)

Because synchronization requires absolute temporal precision, System Real-Time messages cannot wait for multi-byte sequences to finish transmitting. The MIDI specification explicitly allows them to be inserted at any point in the data stream, including between the status byte and data bytes of a standard message, or directly between two data bytes in an ongoing running status stream.

What Occurs During an Interruption

When an unexpected System Real-Time byte arrives during a running status sequence, the receiving device processes the byte immediately without altering its parsing state.

  1. Immediate Processing: The receiver extracts the single-byte real-time command directly from the serial input buffer and executes it instantaneously (e.g., advancing the clock counter or starting playback).
  2. Buffer Preservation: The System Real-Time message does not alter, overwrite, or clear the stored running status byte.
  3. Seamless Resumption: The receiver immediately returns to interpreting subsequent bytes as data bytes belonging to the previously stored running status.

For example, if a transmitter sends a Note On status byte followed by note and velocity data, a 0xF8 Timing Clock byte may arrive between a note number and its velocity byte. A properly compliant receiver executes the clock tick and treats the following byte as the velocity byte belonging to the active Note On running status.

The Exception: System Reset (0xFF)

The only System Real-Time message that terminates running status is System Reset (0xFF).

When a receiver encounters a 0xFF byte, it must reset all internal states to their default power-up conditions. This action explicitly clears the running status buffer, turns off active voices, and requires any subsequent MIDI transmission to declare a complete status byte before sending data bytes.
