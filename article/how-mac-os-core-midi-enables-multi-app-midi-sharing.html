How macOS CoreMIDI Enables Multi-App MIDI Sharing

macOS CoreMIDI natively allows multiple applications to read from and write to the same MIDI hardware simultaneously through a centralized system daemon architecture. Rather than permitting individual applications to open exclusive, low-level handles to hardware devices, macOS abstracts all physical MIDI ports via the MIDIServer process. This article details the technical mechanisms—including driver isolation, event broadcasting, stream merging, and host-time synchronization—that enable seamless multi-client MIDI access on macOS.

The Centralized MIDIServer Architecture

The core of macOS MIDI handling is a background system daemon called MIDIServer. In traditional or legacy audio operating systems, opening a connection to a hardware port often creates an exclusive lock on that peripheral, preventing any secondary process from accessing the device.

CoreMIDI bypasses hardware locking by strictly decoupling applications from physical hardware drivers. Hardware vendors provide CoreMIDI driver bundles (typically working over standard USB-MIDI class drivers or proprietary I/O Kit drivers), but these drivers are loaded and managed exclusively by MIDIServer. The daemon acts as the sole owner of the physical hardware endpoints, operating as a centralized broker between physical interfaces and user-space applications.

Input Distribution: Broadcasting to Multiple Clients

When physical MIDI hardware transmits data into a Mac:

  1. Hardware Capture: The physical interface receives the electrical or optical signals and sends the data over USB or Thunderbolt to the kernel.
  2. Driver Processing: The device driver, hosted inside MIDIServer, receives the raw byte stream and packages it into CoreMIDI data structures (such as MIDIPacketList for MIDI 1.0 or MIDIEventList for Universal MIDI Packets in MIDI 2.0).
  3. Inter-Process Communication (IPC): When an application launches and initializes a CoreMIDI client (using MIDIClientCreate), it registers interest in specific MIDI sources via MIDIPortConnectSource.
  4. Publish-Subscribe Fan-Out: MIDIServer functions on a publish-subscribe model. Instead of passing the incoming packet list destructively to a single reader, it duplicates the event references across Mach messaging channels to every application subscribed to that hardware endpoint.

Because the data is broadcast concurrently, a digital audio workstation (DAW), a standalone software synthesizer, and a MIDI monitor utility can all read identical, real-time incoming streams from a single keyboard controller with zero interference.

Output Merging: Multiplexing Streams to Hardware

When multiple applications send messages to the same external MIDI output destination simultaneously, CoreMIDI performs a dynamic multiplexing (fan-in) process:

  1. Application Transmission: Each application dispatches its MIDI events to a shared destination endpoint using functions like MIDISend().
  2. Buffer Ingestion: Rather than writing directly to the device registers, the application sends its packet list via IPC to MIDIServer.
  3. Stream Aggregation: MIDIServer receives asynchronous packets from all transmitting processes. It merges these distinct streams into a unified queue destined for the hardware driver.
  4. Hardware Delivery: The underlying device driver pulls from this consolidated buffer and serializes the messages onto the physical connection.

Timing and Synchronization via mach_absolute_time

Concurrent multi-client access risks data collisions and timing jitter if two applications send conflicting or simultaneous messages. CoreMIDI resolves this by requiring events to include high-resolution timestamps based on mach_absolute_time().

When an application schedules an event:

  • Immediate Playback: If an event has a timestamp of 0, it is processed immediately by the server in the order received.
  • Scheduled Playback: If a DAW schedules an event in the future to compensate for audio buffer latency, the timestamp dictates the precise system clock tick at which MIDIServer must deliver the packet to the hardware driver.

This timestamp-based scheduling allows MIDIServer to interleave events from multiple applications in chronologically accurate order, preventing stream corruption and ensuring reliable performance across all active clients.
