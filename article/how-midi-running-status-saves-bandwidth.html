How MIDI Running Status Saves Bandwidth

MIDI running status is an optimization rule within the MIDI 1.0 specification designed to conserve transmission bandwidth and minimize latency over serial connections. In traditional MIDI communication, every command requires a status byte followed by relevant data bytes. When multiple consecutive commands share the same status type and channel—such as rapid chord progressions, dense pitch bends, or continuous controller sweeps—running status permits the transmitter to omit redundant status bytes, reducing total data throughput by up to 33 percent.

Under standard conditions, a channel voice message like a "Note On" consists of three bytes:

  1. Status Byte: Identifies the event type and MIDI channel (e.g., 0x90 for Note On, Channel 1).
  2. Data Byte 1: Identifies the note number (e.g., 0x3C for Middle C).
  3. Data Byte 2: Identifies the velocity (e.g., 0x64 for strike velocity).

Without running status, sending a four-note chord at the same instant requires 12 bytes: four sets of three-byte messages. Because traditional MIDI operates at a fixed, relatively slow baud rate of 31.25 kbps, transmitting each byte takes approximately 320 microseconds. A 12-byte block takes roughly 3.84 milliseconds to transmit, introducing audible timing jitter in dense musical passages.

Running status eliminates this overhead. Once a receiver processes a status byte, it stores that byte in an internal buffer. If the subsequent message uses the exact same status byte, the sender transmits only the new data bytes. The receiver checks the most significant bit (MSB) of incoming bytes:

  • If the MSB is 1 (values 128–255), the byte is recognized as a new status byte, which updates the buffer.
  • If the MSB is 0 (values 0–127), the receiver recognizes it as a data byte and applies the active status stored in its buffer.

Applying running status to the same four-note chord reduces the transmission payload:

  • Note 1: 0x90 (Status), 0x3C (Note), 0x64 (Velocity) — 3 bytes
  • Note 2: 0x40 (Note), 0x64 (Velocity) — 2 bytes
  • Note 3: 0x43 (Note), 0x64 (Velocity) — 2 bytes
  • Note 4: 0x47 (Note), 0x64 (Velocity) — 2 bytes

Total data drops from 12 bytes to 9 bytes, yielding a 25 percent reduction in data volume. For continuous controller streams (like modulation or volume) and pitch bend changes, where the status byte repeats dozens of times in a fraction of a second, bandwidth savings approach the theoretical maximum of 33.3 percent.

Running status also integrates seamlessly with common playing techniques. Because sending a "Note On" with a velocity of zero is treated by the MIDI standard as a "Note Off," a sequence of note attacks and releases on the same channel can run continuously under a single initial 0x90 status byte without ever sending an explicit Note Off (0x80) status byte.

The running status buffer remains active until a new channel message or system common message appears. System Real-Time messages (such as MIDI Clock or Active Sensing) are an exception; they can be inserted anywhere in the data stream without clearing or interrupting the active running status. Through this simple byte-dropping rule, MIDI hardware maximizes throughput and reduces audible latency without requiring higher physical transmission clock rates.
