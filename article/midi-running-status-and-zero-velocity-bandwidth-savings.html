MIDI Running Status and Zero Velocity Bandwidth Savings

Combining MIDI running status with zero-velocity Note Off messages reduces note transmission bandwidth by approximately 33.3%. The standard MIDI 1.0 protocol operates at a fixed serial rate of 31.25 kbaud, meaning byte conservation is essential for minimizing latency and timing jitter in dense musical arrangements. By leveraging running status alongside zero-velocity commands, musicians and hardware developers cut the data required for a complete note cycle from six bytes down to four.

Standard Note Transmission Overhead

Under the standard MIDI 1.0 specification, communicating a single note requires two separate 3-byte events:

  1. Note On (0x9n): Status byte (0x9n), Note Number (0–127), Velocity (1–127) — 3 bytes
  2. Note Off (0x8n): Status byte (0x8n), Note Number (0–127), Release Velocity (0–127) — 3 bytes

Without any protocol optimizations, every played and released note consumes 6 bytes of data.

The Running Status Limitation

MIDI includes a feature called Running Status, which dictates that if consecutive messages share the same status byte, the status byte can be omitted from subsequent transmissions. Under this rule, a 3-byte message is reduced to a 2-byte transmission containing only the data bytes.

However, standard Note On (0x9n) and Note Off (0x8n) messages alternate in regular performance. Because the status byte changes from 0x9n to 0x8n every time a note is released, running status is constantly interrupted. As a result, standard Note Off commands negate the benefits of running status during typical polyphonic keyboard play.

The Zero-Velocity Solution

To solve this problem, the MIDI specification allows a Note On command with a velocity of zero (velocity = 0x00) to act as a Note Off command.

Using this convention, releases no longer require the 0x8n status byte; they use the 0x9n Note On status byte instead. Because both the note activation and note release share the identical 0x9n status byte, running status remains unbroken across continuous streams of notes.

Calculated Bandwidth Savings

Once the initial 0x9n status byte is established, all subsequent note events—both presses and releases—only require the two data bytes (pitch and velocity):

  • Standard Note Cycle: 3 bytes (Note On) + 3 bytes (Note Off) = 6 bytes per note
  • Optimized Note Cycle: 2 bytes (Note On) + 2 bytes (Note Off at velocity 0) = 4 bytes per note

This results in an absolute saving of 2 bytes per note lifecycle:

\[\frac{6\text{ bytes} - 4\text{ bytes}}{6\text{ bytes}} = 33.33\%\]

Practical Impact

At 31.25 kbaud, MIDI transmits roughly 3,125 bytes per second (using standard 10-bit asynchronous framing with one start bit, eight data bits, and one stop bit).

  • Without optimization: The interface handles a theoretical maximum of approximately 520 complete notes per second.
  • With Running Status and Zero-Velocity: The interface can handle approximately 781 complete notes per second.

This 33.3% throughput improvement effectively prevents data bottlenecks during complex polyphonic passages, rapid arpeggios, and dense multitrack sequencing, maintaining precise musical timing over legacy hardware connections.
