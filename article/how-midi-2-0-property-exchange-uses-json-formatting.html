How MIDI 2.0 Property Exchange Uses JSON Formatting

MIDI 2.0 Property Exchange (PE) provides a standardized framework that allows musical instruments and software to negotiate, discover, and configure device settings dynamically over standard MIDI connections. By leveraging JavaScript Object Notation (JSON) inside MIDI-CI (Capability Inquiry) System Exclusive messages, devices can request and interpret complex data structures without proprietary drivers. This article explains how Property Exchange implements JSON schemas to discover device capabilities, inspect parameter names, and retrieve complete patch and preset lists.

The Mechanism of Property Exchange

Property Exchange operates as a core service of MIDI-CI. It functions on a request-and-response model using Universal System Exclusive messages to carry text-based payloads.

Each Property Exchange transaction divides information into two segments:

  1. Header Data: A compact JSON object defining the command type (e.g., GetData, SetData, Subscribe), a resource identifier, transaction IDs, status codes, and optional pagination parameters.
  2. Body Data: The payload containing the actual resource content, which for parameter and patch queries is formatted as a structured JSON object or array.

This architecture enables controllers and Digital Audio Workstations (DAWs) to query unknown hardware and automatically configure controls, display screens, and preset browsers.

Querying Parameter Names and Attributes

In traditional MIDI workflows, mapping a controller to a synthesizer required static definition files or manual MIDI CC mapping. MIDI 2.0 eliminates this through automated parameter discovery:

  1. Resource Discovery: The controller initiates a GetData request for the ResourceList resource to determine which property endpoints the target device supports.
  2. Parameter List Request: The controller issues a GetData command targeting parameters, typically addressing the PropertyList or a custom resource path such as /ch1/parameters.
  3. JSON Response: The responder returns a JSON array detailing every available parameter. A parameter definition in the JSON payload typically includes:
    • id or property: The unique identifier corresponding to a MIDI 2.0 Registered Controller (RC), Assignable Controller (AC), or specific parameter address.
    • title: The human-readable name of the parameter (e.g., "Cutoff Frequency", "Resonance").
    • type: Data type specifications (e.g., integer, boolean, float, string).
    • min, max, and default: The valid value boundaries and default positions.
    • units: Measurement units for contextual display (e.g., "Hz", "dB", "ms").

Because the descriptor is delivered as standard JSON, a controller can immediately parse the schema and dynamically construct a user interface with accurate labels and appropriate control ranges.

Retrieving Patch and Preset Lists

Querying patch, bank, and program lists follows the same structured JSON exchange, replacing legacy binary dump protocols with human-readable hierarchies:

  1. Inquiry: The client device transmits a GetData message targeting the ProgramList resource.
  2. Pagination (Optional): For devices containing thousands of presets, the JSON header can supply pagination keys, such as offset and limit, preventing buffer overruns on resource-constrained hardware.
  3. Structured Response: The target instrument responds with a JSON body representing the hierarchy of banks and presets. A standard entry inside the program list contains:
    • bank: The Bank Select MSB and LSB values required to address the preset.
    • program: The Program Change number (0–127).
    • name: The displayed preset name (e.g., "Warm Analog Pad").
    • category: Optional classification metadata (e.g., "Lead", "Bass", "Strings").

Advantages of JSON in MIDI 2.0

Using JSON within Property Exchange standardizes communication between disparate platforms and architectures. Because JSON natively supports nested trees, key-value mappings, and text encoding, instruments can communicate complex state representations cleanly. Software DAWs, hardware controllers, and synthesizers can reliably auto-populate menus, map encoders, and display active patch configurations without relying on manual setup or vendor-specific software editors.
