BLE-MIDI Packet Payload Encapsulation Explained

This article examines the payload encapsulation format utilized by the MIDI over Bluetooth Low Energy (BLE-MIDI) specification to transmit MIDI events over BLE characteristics. It breaks down the precise byte structure of BLE-MIDI packets, explaining how standard MIDI messages are wrapped alongside 13-bit timestamp data to mitigate transmission jitter, as well as how running status, packet batching, and System Exclusive (SysEx) fragmentation are handled within the Bluetooth Generic Attribute Profile (GATT) framework.

GATT Transport Architecture

BLE-MIDI operates over a standard Bluetooth GATT profile consisting of a single custom service and a single characteristic. This characteristic handles bi-directional data flow using Write Without Response from the client (central) to the server (peripheral) and Notify from the peripheral to the client. Because BLE transmission introduces variable connection interval latencies, standard raw MIDI streaming is insufficient. BLE-MIDI solves this by wrapping standard MIDI 1.0 messages with timing metadata inside the characteristic's payload.

The BLE-MIDI Packet Structure

Every BLE-MIDI characteristic value payload consists of a mandatory Header Byte, followed by one or more sequences of a Timestamp Byte and a MIDI Message. A single BLE-MIDI payload must fit within the negotiated Maximum Transmission Unit (MTU) minus the 3-byte ATT header overhead.

+-------------+----------------+--------------+----------------+--------------+
| Header Byte | Timestamp Byte | MIDI Message | Timestamp Byte | MIDI Message | ...
+-------------+----------------+--------------+----------------+--------------+

1. The Header Byte

The very first byte of any BLE-MIDI payload is the Header Byte. It serves two functions: identifying the start of a BLE-MIDI transmission and delivering the upper bits of the timing system.

  • Bit 7: Must always be 1 (identifies it as a header/status byte).
  • Bit 6: Reserved for future use (currently set to 0).
  • Bits 5–0: Timestamp High (timestamp[12:7]). Contains the upper 6 bits of a 13-bit timestamp.

2. The Timestamp Byte

Immediately following the Header Byte (or preceding a new MIDI event in a multi-message packet), a Timestamp Byte is inserted.

  • Bit 7: Must always be 1.
  • Bits 6–0: Timestamp Low (timestamp[6:0]). Contains the lower 7 bits of the 13-bit timestamp.

Together, the 6 bits from the Header Byte and the 7 bits from the Timestamp Byte form a 13-bit millisecond counter ((Timestamp_High << 7) | Timestamp_Low). This 13-bit value ranges from 0 to 8,191 milliseconds and wraps continuously. Receivers use these timestamps to reconstruct the original inter-message timing and eliminate jitter caused by BLE connection intervals.

3. The MIDI Message Bytes

Following the Timestamp Byte are standard MIDI 1.0 bytes:

  • Status Byte: A standard MIDI status byte (e.g., 0x90 for Note On), with Bit 7 set to 1.
  • Data Bytes: Standard data bytes (e.g., note number and velocity), with Bit 7 set to 0.

Because both the BLE-MIDI Timestamp Byte and MIDI Status Bytes have Bit 7 set to 1, parsers distinguish them contextually: the byte immediately following a Header Byte is always a Timestamp Byte, and any byte with Bit 7 set to 1 occurring where a status byte is expected is processed as a MIDI Status Byte.

Multiple Messages and Running Status

BLE-MIDI allows multiple MIDI messages to be packed into a single BLE packet to maximize bandwidth efficiency:

  • Consecutive Messages with Different Timestamps: If multiple events occur within the same BLE packet but at different times, a new Timestamp Low byte (1xxxxxxx) precedes the subsequent MIDI Status Byte. The Timestamp High remains governed by the packet's Header Byte unless an internal timer wrap occurs.
  • Consecutive Messages with the Same Timestamp: If multiple messages occur at the exact same millisecond, the subsequent message can immediately follow the previous data byte without inserting a duplicate Timestamp Byte.
  • Running Status: BLE-MIDI supports standard MIDI running status. When consecutive messages share the same status byte (e.g., multiple Note On events), subsequent messages omit the MIDI Status Byte. If the timestamp changes, the format becomes: [Timestamp Byte] [Data Byte 1] [Data Byte 2].

System Exclusive (SysEx) Encapsulation

SysEx messages, which often exceed the standard BLE MTU size, are fragmented across multiple BLE-MIDI packets:

  • Start Packet: Begins with the Header Byte, followed by a Timestamp Byte, the SysEx Start status byte (0xF0), and the initial data bytes.
  • Continuation Packet: Begins with the Header Byte, but omits the SysEx Start status byte, providing only raw SysEx data bytes. A Timestamp Byte may be inserted if required.
  • End Packet: Ends with the SysEx End status byte (0xF7), which must be immediately preceded by a Timestamp Byte to specify the precise termination time of the message.
