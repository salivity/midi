Measure USB MIDI Latency with a Hardware Echo Loop

Accurately measuring round-trip USB driver latency requires isolating software stack overhead and buffer scheduling from external variables. By physically bridging a MIDI interface’s output to its input, an engineer creates a closed hardware echo loop. A host application then transmits timestamped MIDI packets, captures their return, subtracts known physical wire transmission times, and computes the driver and operating system round-trip latency (RTL). This process provides direct insight into USB polling intervals, buffer jitter, and driver efficiency.

1. Hardware Loopback Configuration

To configure the physical loopback:

  1. DIN-5 Interfaces: Connect a standard, low-capacitance MIDI cable directly from the interface’s MIDI OUT port to its MIDI IN port. The optocoupler on the input stage introduces a negligible propagation delay (typically under 1 to 2 microseconds for standard 6N138 or PC900 optocouplers), which falls well below USB polling resolution.
  2. TRS MIDI Interfaces: Use the correct Type A or Type B TRS-to-DIN or TRS-to-TRS adapter to route the tip/ring signals back into the input stage without phase inversion.
  3. Connection to Host: Plug the MIDI interface directly into a native root USB port on the test machine. Avoid external hubs or daisy-chained Thunderbolt docks, as these introduce variable packet scheduling delays.

2. Physical Layer Delay Compensation

Standard serial MIDI operates at 31,250 baud (bits per second) using asynchronous serial transmission (1 start bit, 8 data bits, 1 stop bit = 10 bits per byte).

  • Each transmitted MIDI byte requires exactly: \[\text{Time per byte} = \frac{10\text{ bits}}{31,250\text{ bps}} = 0.320\text{ ms } (320\text{ }\mu\text{s})\]
  • A standard 3-byte Channel Voice message (such as Note On: 0x90 0x3C 0x64) takes \(3 \times 320\text{ }\mu\text{s} = 0.960\text{ ms}\) strictly to clear the UART hardware shift register on both the transmit and receive passes.

To isolate the USB driver latency, this physical serialization time must be subtracted from the total measured loopback duration unless using high-speed non-standard MIDI implementations.

3. Software and Measurement Architecture

Do not use high-level Digital Audio Workstations (DAWs) for this measurement, as their internal audio-buffer-aligned scheduling alters raw MIDI dispatch times. Instead, use a low-level benchmarking utility (such as alsa-midi-latency-test on Linux) or a custom C/C++ measurement loop using native APIs (such as CoreMIDI on macOS or WinMM/DirectMusic/MIDI 2.0 on Windows).

Implement the measurement loop using the following logic:

  1. Acquire Monotonic Timestamps: Use the host operating system's highest-resolution timer (e.g., clock_gettime(CLOCK_MONOTONIC) on Linux or QueryPerformanceCounter on Windows).
  2. Send Single Events: Transmit a single 3-byte MIDI event or single-byte real-time message (such as 0xF8 MIDI Clock, which takes only \(320\text{ }\mu\text{s}\) over serial lines). Record timestamp \(T_{\text{start}}\).
  3. Capture the Echo: In an asynchronous event listener, capture the incoming bytes. As soon as the final byte of the message is received by the input buffer, record timestamp \(T_{\text{end}}\).
  4. Compute Delta: Calculate total round-trip time: \[\text{Total RTL} = T_{\text{end}} - T_{\text{start}}\]
  5. Normalize Driver Latency: Calculate pure driver/stack latency by subtracting the physical serialization overhead: \[\text{Driver Latency} = \text{Total RTL} - \text{UART Overhead}\]

4. Data Sampling and Jitter Analysis

Single-packet measurements do not reflect real-world performance due to USB frame scheduling. USB Full-Speed endpoints poll at 1 ms frame boundaries, while High-Speed endpoints use 125 \(\mu\text{s}\) microframes.

  • Iteration: Send between 1,000 and 5,000 test messages spaced at randomized intervals (e.g., 20 ms to 50 ms apart) to avoid harmonic synchronization with the host OS thread scheduler or USB frame clock.
  • Metrics: Compute the mean, median, standard deviation, and maximum latency.
  • Evaluation: A low median with a high standard deviation indicates USB transfer buffer queuing issues or aggressive operating system power-saving states (CPU C-states). A high, consistent median indicates unoptimized driver buffer depths or large USB endpoint polling intervals (bInterval).
