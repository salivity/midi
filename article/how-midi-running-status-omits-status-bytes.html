How MIDI Running Status Omits Status Bytes

This article explains the mechanism of "running status" in the MIDI specification, demonstrating how it reduces data transmission overhead during continuous note playback. By allowing a MIDI transmitter to send subsequent data bytes without repeating the initial command, running status conserves precious bandwidth on legacy serial connections, prevents message lag, and maintains tight musical timing during complex, note-heavy performances.

The Structure of a Standard MIDI Message

To understand running status, it is essential to first examine how standard MIDI messages are formatted. A typical Channel Voice message, such as a Note On command, consists of three bytes:

  1. Status Byte: Identifies the command type and channel (e.g., 0x90 represents a Note On command on Channel 1). The most significant bit (MSB) of a status byte is always set to 1 (binary values ranging from 10000000 to 11111111).
  2. Data Byte 1: Identifies the pitch or note number (e.g., 0x3C for Middle C). The MSB of all data bytes is always set to 0 (binary values ranging from 00000000 to 01111111).
  3. Data Byte 2: Specifies the velocity or intensity of the note (e.g., 0x64).

Under normal operation without optimization, playing three consecutive notes requires nine bytes of transmission: [Status, Data 1, Data 2], [Status, Data 1, Data 2], and [Status, Data 1, Data 2].

The Mechanism of Running Status

Running status operates on a simple principle: if a sequence of MIDI messages shares the exact same status byte, the transmitter can omit the status byte for every message after the first one.

Because the MIDI protocol strictly dictates that status bytes begin with a binary 1 and data bytes begin with a binary 0, a receiving device can instantly distinguish between the two. When the receiver detects a data byte where a status byte was expected, it does not discard the byte as an error. Instead, it refers to its internal buffer, assumes the previously received status byte is still active, and processes the incoming data bytes accordingly.

For example, a continuous stream of three Note On events on Channel 1 is transmitted as follows:

  • Initial Message: 0x90 (Status), 0x3C (Note), 0x64 (Velocity)
  • Second Message: 0x3E (Note), 0x64 (Velocity)
  • Third Message: 0x40 (Note), 0x64 (Velocity)

By dropping the repeated 0x90 status byte, the total transmission size for the three notes drops from nine bytes to seven bytes.

Leveraging "Note On with Velocity Zero"

In standard MIDI, stopping a note requires a Note Off message (0x80 on Channel 1). If a performance alternated between standard Note On (0x90) and Note Off (0x80) commands, the status byte would constantly change, disabling running status and requiring three bytes per event.

To bypass this limitation, the MIDI specification allows a Note On command with a velocity of zero (0x00) to act as a Note Off. This allows a continuous stream of note presses and releases to share a single running status byte:

  • 0x90 0x3C 0x64 — Note On: C4, Velocity 100 (Establishes running status)
  • 0x3E 0x64 — Note On: D4, Velocity 100
  • 0x3C 0x00 — Note Off: C4 (Treated as Note On with Velocity 0)
  • 0x3E 0x00 — Note Off: D4 (Treated as Note On with Velocity 0)

Through this method, an entire sequence of polyphonic notes can be initiated and terminated using only pairs of data bytes.

Bandwidth Savings and Timing Integrity

The primary benefit of running status is bandwidth conservation. MIDI 1.0 operates over a slow, 5-pin DIN serial connection fixed at 31,250 baud (bits per second), allowing roughly 1,000 standard three-byte messages per second.

By eliminating the status byte from recurring messages, running status reduces the data footprint of note events by 33%. In dense musical passages, glissandos, arpeggios, or rapid multi-voice sequences, this reduction prevents the serial pipeline from choking, directly minimizing latency and audible timing jitter.
