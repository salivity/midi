How MIDI-CI Switches from MIDI 1.0 to MIDI 2.0

MIDI Capability Inquiry (MIDI-CI) provides a standardized mechanism that allows backward-compatible devices to query each other and expand their communication capabilities. This article explains the step-by-step process of how MIDI-CI Protocol Negotiation enables two connected units to safely transition an active connection from legacy MIDI 1.0 to the high-resolution, bidirectional MIDI 2.0 environment.

1. Initial State and Discovery

All MIDI connections begin under the assumption of legacy MIDI 1.0 operation. Because legacy hardware may not understand new message formats, devices must communicate exclusively through standard MIDI 1.0 Universal System Exclusive (SysEx) messages until compatibility is verified.

Before negotiation begins, devices perform a Discovery process:

  • Each device generates a 28-bit MIDI Unique Identifier (MUID).
  • The initiating device sends a Discovery inquiry SysEx message.
  • If the receiving device supports MIDI-CI, it replies with its own MUID and a profile of supported MIDI-CI categories: Protocol Negotiation, Profile Configuration, and Property Exchange.

2. Inquiring Supported Protocols

Once mutual MIDI-CI support is established, the initiator queries the responder's supported communication formats.

  1. Protocol Inquiry Message: The initiator sends a SysEx message requesting a list of supported protocols.
  2. Protocol Inquiry Reply: The responder returns a list of protocols it can handle. This list indicates whether the device supports:
    • MIDI 1.0 (Byte Stream or Universal MIDI Packet)
    • MIDI 2.0 (Universal MIDI Packet)
    • Specific protocol extensions, such as jitter reduction timestamps.

3. Setting the Protocol

If both devices support MIDI 2.0, the initiator formally requests the transition.

  1. Set New Protocol: The initiator sends a "Set New Protocol" message specifying MIDI 2.0 as the desired active protocol.
  2. Test and Acknowledgment: Before permanently switching, the responder validates whether it can operate reliably at the requested protocol. It replies with an acknowledgment confirming that it is prepared to switch. In some implementations, a protocol test message is sent to verify that the transport layer does not corrupt or drop packets.

4. The Transition to Universal MIDI Packet (UMP)

Upon successful confirmation, both devices switch their active data parsers:

  • Message Framing: Data ceases to flow as variable-length legacy MIDI 1.0 byte streams. Instead, both units begin sending and receiving Universal MIDI Packets (UMP)—structured 32-bit words (ranging from 32 to 128 bits per message).
  • Feature Access: The devices can now use native MIDI 2.0 Channel Voice Messages, unlocking 32-bit resolution for velocity and controllers, per-note pitch bend, per-note controllers, and 256 individual channels grouped across 16 UMP groups.

5. Fallback and Redundancy

Reliability is built directly into the negotiation workflow. If the responder fails to acknowledge the "Set New Protocol" request within a designated timeout window, or if an error message is returned, both devices immediately drop back to MIDI 1.0. Furthermore, if a physical disconnection occurs, the devices revert to baseline MIDI 1.0 upon reconnection until a new MIDI-CI handshake is executed.
