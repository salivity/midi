MIDI Capability Inquiry Message Format Explained

This article explores the MIDI Capability Inquiry (MIDI-CI) message format, detailing its core architecture, operational functions, and role in modern music technology. Serving as the primary bridge between legacy MIDI 1.0 devices and the modern MIDI 2.0 specification, MIDI-CI defines a standardized mechanism for digital musical instruments to automatically query each other, negotiate capabilities, and configure advanced data streams without requiring manual configuration.

The Core Purpose of MIDI-CI

Historically, the original MIDI 1.0 specification functioned strictly as a one-way communication protocol. A transmitting device sent control signals without knowing if the receiving device was capable of interpreting them.

MIDI-CI transforms this paradigm by establishing a standardized, bidirectional discovery and negotiation protocol. Before sending high-resolution performance data or custom configurations, devices use the MIDI-CI message format to ask:

  • Who are you?
  • What features do you support?
  • Can we communicate using MIDI 2.0?

By enabling devices to discover mutual capabilities, MIDI-CI ensures seamless backward compatibility while unlocking advanced features whenever supported hardware or software is detected.

The Three Core Functions of MIDI-CI

The MIDI-CI message format operates across three specialized functional areas:

1. Protocol Negotiation

Protocol Negotiation is the mechanism that allows devices to transition from standard MIDI 1.0 to modern MIDI 2.0 protocols. Through CI messages, a device requests whether the connected instrument can support the Universal MIDI Packet (UMP) format and MIDI 2.0 high-resolution velocity, articulation, and timing. If both devices agree, the connection upgrades automatically; if either device declines, communication safely defaults to standard MIDI 1.0.

2. Profile Configuration

Profiles are pre-defined sets of rules and controller behaviors for specific instrument types (such as drawbar organs, analog synthesizers, or orchestral sample libraries). The MIDI-CI Profile Configuration format allows devices to query supported profiles, turn specific profiles on or off, and map hardware controls to matching parameters systematically, minimizing the need for manual MIDI mapping.

3. Property Exchange

Property Exchange allows devices to transfer rich metadata, configuration parameters, and state information using standard web formats like JSON. Via MIDI-CI Property Exchange messages, a synthesizer can transmit patch names, parameter names, controller assignments, and visual editor data directly to a digital audio workstation (DAW) or hardware controller.

Anatomy of the MIDI-CI Message Format

MIDI-CI messages are constructed using Universal System Exclusive (SysEx) structures, ensuring they can travel over legacy MIDI 1.0 DIN cables, USB connections, and network interfaces without corrupting non-compatible devices.

A standard MIDI-CI message includes the following structural components:

  • SysEx Header: Standard MIDI framing (F0 start and F7 termination).
  • Universal System Exclusive Sub-ID: Identifies the packet as a MIDI-CI message (Sub-ID 1: 0x0D).
  • Sub-ID 2 (CI Message Category): Denotes the exact CI function, such as Discovery, Profile Configuration, Property Exchange, or Protocol Negotiation.
  • CI Message Version: Identifies the version of the MIDI-CI specification being used.
  • Source and Destination MUIDs: MIDI-CI introduces 28-bit Device Unique Identifiers (MUIDs). Every device randomly generates an MUID upon connection, allowing multiple devices sharing a single bus to target messages accurately to specific endpoints.
  • Payload: The specific request or response data corresponding to the selected CI category.

Through this structured inquiry-and-response architecture, the MIDI-CI format guarantees that modern musical hardware and software remain auto-configuring, communicative, and universally compatible.
