RTP-MIDI Recovery Journal: Reconstructing Lost Packets

The Real-Time Transport Protocol payload format for MIDI (RTP-MIDI) relies on a specialized mechanism called the Recovery Journal to maintain performance integrity over unreliable networks like Wi-Fi. Because standard retransmission protocols like TCP introduce unacceptable latency for musical performance, RTP-MIDI uses UDP and embeds historical state snapshots within packet headers. This overview explains how the Recovery Journal detects lost sequence numbers and reconstructs critical MIDI control data—such as Control Change, Pitch Bend, and Note-Off events—without requiring the sender to retransmit dropped packets.

The Challenge of Real-Time MIDI Over Wi-Fi

Wi-Fi networks are inherently prone to burst packet loss, channel interference, and jitter. Traditional transmission control protocols rely on Acknowledgement (ACK) and Automatic Repeat reQuest (ARQ) strategies to resend missing data. For musicians and live performance audio systems, the round-trip delay caused by retransmissions breaks timing synchronization and can cause fatal errors, such as stuck "hanging" notes or missed modulation changes.

RTP-MIDI solves this through forward error correction and state-tracking concepts standardized in RFC 6295, utilizing the Recovery Journal to achieve near-instantaneous state synchronization after a packet is lost.

Architecture of the Recovery Journal

Every RTP-MIDI packet consists of a standard RTP header, a MIDI command payload containing newly executed commands, and an optional Recovery Journal (RJ).

The journal represents a condensed history of recent MIDI events. Instead of sending raw duplicates of previous MIDI streams, the journal organizes data into dedicated "Chapters" categorized by MIDI channel and command type:

  • Chapter N (Note-On / Note-Off): Tracks active notes and pairs Note-On events with corresponding execution counters to prevent hanging notes.
  • Chapter C (Control Change): Stores the most recent values for continuous controllers (CC), including modulation, volume, and expression.
  • Chapter W (Pitch Wheel): Retains the latest pitch bend positions.
  • Chapter P (Program Change): Maintains the active patch or preset selections.
  • Chapter A and M (Aftertouch): Preserves polyphonic and channel pressure values.
  • System Chapters: Captures system real-time, exclusive (SysEx), and common messages.

How the Receiver Reconstructs Lost Control Packets

The reconstruction process depends on sequence numbers embedded in the RTP header and the checkpoint timestamps inside the Recovery Journal:

  1. Loss Detection: The receiver continuously monitors the RTP packet sequence counter. If packet N arrives immediately after packet N-2, the receiver detects that packet N-1 was dropped in transit.
  2. Journal Inspection: Instead of requesting a retransmission of packet N-1, the receiver inspects the Recovery Journal attached to packet N.
  3. Parameter Reconciliation: The receiver checks the journal chapters covering the sequence range of the missing packet. Because MIDI controllers largely represent state changes (e.g., set Modulation Wheel to value 64), the receiver does not necessarily need every intermediate step; it only requires the current state at the time of packet N.
  4. Execution and State Update: The receiver executes the updated parameter values extracted from the journal (such as sending a missing Note-Off or adjusting the controller to its latest position) concurrently with the new payload in packet N.

Channel Controller Management

For high-density control data, such as expression pedals or modulation wheels, Wi-Fi congestion frequently drops multiple intermediate values. The Recovery Journal handles this through controller log bitmasks.

Chapter C stores the most current value of each altered controller along with an encoded list indicating which controllers changed since the journal's reference checkpoint. When packet loss occurs, the receiver updates the target controller directly to the snapshot state contained in the next successful packet, entirely bypassing the missing intermediate steps and eliminating audible artifacts or parameter lag.

Through this proactive state-mirroring method, RTP-MIDI guarantees musical continuity across degraded Wi-Fi connections with zero added round-trip latency.
