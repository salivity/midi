How RTP-MIDI Encapsulates MIDI Over UDP

RTP-MIDI, standardized under RFC 6295, is a network protocol that transmits standard MIDI communication streams across local area networks using standard Internet Protocol architecture. By packaging musical control data inside the Real-time Transport Protocol (RTP) and transmitting it via the User Datagram Protocol (UDP), RTP-MIDI eliminates the physical limitations of legacy 31.25 kbaud 5-pin DIN cables. This article breaks down how RTP-MIDI maps serial MIDI messages into modern network datagrams, preserves microsecond-level timing across network switches, and compensates for UDP packet loss using an active recovery journal.

The Network Stack: Why UDP?

Traditional MIDI relies on a point-to-point, continuous serial stream. When moving this stream to an IP network, Transmission Control Protocol (TCP) is unsuitable because its retransmission mechanism (acknowledgments and handshakes) introduces unpredictable latency and jitter, which ruins musical timing.

Instead, RTP-MIDI utilizes UDP at the transport layer. UDP provides connectionless, low-overhead transmission, allowing packets to move instantly across a local area network (LAN). Because UDP does not guarantee packet arrival or ordering, RTP-MIDI relies on the RTP layer (RFC 3550) sitting directly above UDP to supply sequencing, timestamping, and payload identification.

Anatomy of an RTP-MIDI Packet

When a musician plays a note or moves a continuous controller, the local RTP-MIDI driver constructs a network packet containing three nested layers:

  1. UDP Header: Specifies the source and destination port numbers. AppleMIDI (a common implementation of RTP-MIDI) typically utilizes dynamic ports negotiated via control sessions, often starting around port 5004.
  2. RTP Fixed Header: A 12-byte standard header containing:
    • Sequence Number: Increments with every packet sent, allowing the receiver to detect missing or out-of-order packets.
    • Timestamp: A 32-bit clock value (typically running at a 10 kHz or 44.1/48 kHz reference clock) representing the exact execution time of the commands inside.
    • Synchronization Source (SSRC) Identifier: Distinguishes the specific MIDI device or stream from other senders on the same network.
  3. RTP-MIDI Payload: The specialized data segment containing the actual performance instructions.

The RTP-MIDI Payload Structure

The payload section wraps raw MIDI messages inside structured sub-headers:

  • Payload Header Flags: A set of bit flags that define how the packet is formatted. These include flags such as the B (Big) flag (indicating whether the header uses 1 or 2 octets), the J (Journal) flag (indicating the presence of a recovery journal), and the Z flag (handling time-synchronization data).
  • Command Section: Contains the serialized MIDI messages. Instead of sending bare MIDI bytes, messages are prefaced with a "Delta-Time" value. This delta-time indicates the relative micro-delay between consecutive MIDI events within the same packet, preserving human performance nuance and chord structures. Multiple MIDI commands (like Note-On, Pitch Bend, and Control Change) can be packed into a single payload to conserve bandwidth.

Precision Timing and Jitter Buffering

Networked audio and MIDI require stable phase coherence. Standard network packet delivery suffers from latency jitter—minor variations in packet arrival times caused by network switches and operating system queues.

To solve this, RTP-MIDI uses its RTP timestamps to schedule event execution:

  • The sender calculates an RTP timestamp matching the intended performance time.
  • The receiving device buffers incoming packets slightly (often 1 to 2 milliseconds).
  • The receiver executes the MIDI commands not when the packet physically arrives, but when the receiver's local clock matches the timestamp inside the RTP header. This renders the stream completely immune to transmission jitter, assuming the jitter does not exceed the buffer window.

Handling Packet Loss: The Recovery Journal

Because UDP does not retransmit lost packets, a dropped packet could cause catastrophic musical errors, such as a "stuck note" (where a Note-Off message is dropped) or an unreset sustain pedal.

RTP-MIDI resolves this through an optional, highly efficient mechanism called the Recovery Journal. When enabled:

  • Each packet includes a snapshot of recent channel states alongside the new MIDI commands.
  • The journal stores the state of currently active notes, controller values (like modulation or volume), program changes, and system exclusive transfers across past sequence numbers.
  • If the receiver detects a gap in sequence numbers (e.g., it receives packet #12 after packet #10), it inspects the recovery journal in packet #12. The journal tells the receiver which notes should currently be sounding and which controllers have changed, allowing the receiver to instantly update its local synthesizer engine and silence dead notes without requesting a retransmission.
