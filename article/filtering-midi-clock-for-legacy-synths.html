Filtering MIDI Clock for Legacy Synths

Dedicated MIDI processing boxes prevent vintage synthesizers from crashing, lagging, or dropping notes by intercepting incoming serial data, identifying high-frequency real-time commands such as MIDI clock, and discarding those specific bytes before transmitting note data to the output. Older synthesizers rely on slow microprocessors and small input buffers that easily become overwhelmed by modern master clocks and synchronization data. By stripping away these continuous messages at the hardware level, a processing box preserves critical bandwidth and ensures that only performance messages reach legacy hardware.

The Problem with Real-Time Data on Vintage Hardware

MIDI is an asynchronous serial protocol operating at a rate of 31.25 kbaud. A master sequencer sends a MIDI Timing Clock message 24 times per quarter note (24 PPQN), alongside Start, Stop, and Active Sensing messages. While modern gear handles this influx without issue, vintage synthesizers—many powered by modest 8-bit microcontrollers from the 1980s—must trigger an interrupt routine for every single byte received. When flooded with constant clock pulses, the vintage synthesizer's CPU spends most of its processing cycles handling interrupts rather than generating sound, resulting in audible latency, hanging notes, or total freeze-ups.

Byte-Level Inspection

A hardware MIDI processor features a dedicated microcontroller or FPGA equipped with a Universal Asynchronous Receiver-Transmitter (UART). The processor reads the serial bitstream entering its 5-pin DIN input port and reconstructs the data into raw 8-bit bytes.

MIDI messages fall into distinct categories defined by the value of their first byte:

  • Status Bytes: Always have their most significant bit set to 1 (values 0x80 to 0xFF).
  • Data Bytes: Always have their most significant bit set to 0 (values 0x00 to 0x7F).
  • System Real-Time Bytes: A specific subset of status bytes ranging from 0xF8 to 0xFF.

Among real-time bytes, 0xF8 represents the MIDI Timing Clock, 0xFA through 0xFC control playback transport (Start, Continue, Stop), and 0xFE represents Active Sensing.

The Interception and Stripping Process

Because MIDI specification allows System Real-Time messages to be inserted anywhere in the data stream—even in the middle of a multi-byte Note On or Pitch Bend sequence—the processor cannot simply parse whole phrases at once. Instead, it evaluates every byte immediately upon reception:

  1. Byte Interception: The processor receives a byte in its hardware input buffer.
  2. Bitwise Comparison: The processor checks if the byte is greater than or equal to 0xF8. If it matches a defined filter rule (such as 0xF8 for clock), the processing unit flags it.
  3. Discarding: The flagged byte is dropped entirely from memory and is not passed to the output queue.
  4. Running Status Handling: If a real-time byte arrives between a Status byte (e.g., Note On 0x90) and its parameters (e.g., Key Number 0x3C, Velocity 0x64), discarding the real-time byte ensures the original multi-byte structure remains intact without invalidating the running status logic.

Transmission to the Synth

Bytes that are not flagged for removal—primarily Channel Voice messages like Note On (0x9n), Note Off (0x8n), Control Change (0xBn), and Program Change (0xCn)—are immediately routed to the processor's output UART buffer.

The sanitized data is converted back into an electrical serial stream and transmitted to the synth via the output port. Because the hardware performs this check in clock cycles rather than milliseconds, latency is virtually undetectable (typically well under 1 millisecond), allowing the legacy synthesizer to play reliably with accurate timing.
